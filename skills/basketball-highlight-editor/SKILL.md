# Personal basketball highlights

Use `scripts/highlight.py` to create a resumable project. All script processing is local; no network calls, automatic package installs, video uploads, GUI internals or private project formats. BHE detection and people identification are separate tasks. A candidate is not a confirmed basket; a visible player is not necessarily the shooter.

## Workflow

1. **Receive the local video.** Inspect existing dependencies with `doctor`. Record its processing rights and source in a rights JSON, then `init`. Reuse an installed BHE runtime or an existing read-only DMG. Explain and obtain any necessary authorization before new downloads, software installation or external uploads. Do not install BHE just to use this skill.
2. **Find candidate plays first.** Use the public BHE source CLI through `detect --backend bhe`; supply the runtime directory, validate hoop ROI and retain raw detections, commands, logs and source/model hashes. Read [runtime details](references/runtime.md) for the tested interface. On failure, report the error. `motion-coverage` is an explicit low-specificity fallback that covers the video with overlapping windows; label those as review windows, never detected baskets. `import-candidates` accepts portable time ranges from user-exported BHE clips or another local detector. `add` repairs missed ranges. Avoid claiming complete recall from a scoring-only detector.
3. **Summarize visual evidence before asking who to edit.** Run `features` under a Python with OpenCV and NumPy; use `--no-ocr` when the players have no numbers. It saves sampled full frames, proposed clothing crops, color statistics and optional unverified OCR hints. HOG is used if present; otherwise color regions include non-people. Open `review.html`, inspect the original frames, and offer visual player cards. Report unknown numbers as unknown. Local script features do not autonomously establish a person’s identity. Codex visual review, if used, must be recorded as `agent_visual_review`, not local model inference or human confirmation.
4. **Ask which player.** Show reference images and ask the user to choose a visual card or point to a person. Do not assume jerseys have numbers. For an unnumbered player, first ask the user to confirm a full-body sample; use `sample` to save its timestamp, bounding box, clothing description and the actual confirmation reference. Prefer two clear views when teammates dress similarly. Compare shirt sleeves, shorts, shoes/socks and other stable clothing, with short-range continuity evidence. Optical flow is only a proposal and stops on failure; it cannot safely bridge occlusion, camera cuts or lookalikes. If evidence is insufficient, keep the candidate uncertain and request a better sample. Do not use faces, body size, team color alone or an invented confidence percentage as an identity substitute.
5. **Make the rough selection.** Record evidence-backed player profiles and per-candidate assignments with `annotate`, then `select` using the user’s actual answer. High confidence requires a visible verified number or a saved confirmed sample match, with timestamps and a reason. A color match alone cannot enter that group. Record `role` such as shooter, ball handler, off-ball defense or merely visible; do not label someone’s presence as their made basket. Use `needs_review` for overlap, uncertain role or editorial questions even when identity is clear. Run `rough` to produce separate high-confidence and uncertain clips plus CSV and HTML. Keep excluded items and raw evidence recoverable. “All” means all supported matches among these candidates, not every possible involvement in the source recording.
6. **Have the user review the clips.** They may reply with keep/reject IDs or use the local HTML form to download a decision JSON. Include all high-confidence and uncertain IDs. Read the current revision before applying decisions; stale or incomplete review is rejected. Never invent a human reply. Tests must use `reviewer_kind: test_operator`, clearly distinguished from `user`.
7. **Stop after confirmation.** `confirm` writes `confirmed-edl.json` and enters `awaiting_edit_prompt`. Preserve the project, source reference, evidence and rough media. Do not call `version --render` in the same action merely because selection was confirmed. Tell the user the project is ready and wait for their next editing prompt.
8. **Make versions only on a later prompt.** Translate that prompt into an explicit version spec (clip order, selected IDs, duration cap and prompt text), then `version`. Render only if requested. New versions draw from the same confirmed master and cannot reintroduce rejected candidates. The tested renderer supports clean landscape cuts and duration caps. Music, subtitles, smart reframing, slow motion and editable CapCut/Jianying projects require a separate verified workflow; do not claim they are implemented here.

## Commands and project state

Read [commands and schemas](references/workflow.md) when operating the CLI. `project.json` is authoritative; `candidates.csv` and `review.html` are review surfaces, and `confirmed-edl.json` is the portable cut list. Keep the original video available and unchanged; every mutation checks its SHA256. A new selection, annotation, sample or candidate invalidates confirmation. Tests: `python3 -m unittest discover -s <skill>/tests -v`.

For measured results and the deliberately small public test corpus, read [validation and limits](references/validation.md). Do not present test-operator confirmations as user approval or extrapolate this smoke test to reliable unnumbered-player recognition in a full game.
